# 池健康面板 · 组件设计方案（`PoolHealthPanel`）

> 面向「统计页」的可集成组件。目标单一：**一眼分辨「配额不足」与「服务故障」**。
> 实现：`workbuddy-switch/src/components/pool-health-panel.tsx`（2.1.1 起）。

---

## 1. 问题定义

两类故障**症状同形**（客户端都是 `503` / `无可用账号`），但处置完全相反：

| | 配额不足 | 服务故障 |
| --- | --- | --- |
| 成因 | 上游按**模型**限流（频率上限）| 熔断 / 出池 / 链路不通 |
| 判据信号 | `model_cools` 命中 | `breaker_until` / `disabled` / 传输错误 |
| 正确处置 | 等重置、换模型、加账号 | 排查出口、等熔断退避 |
| 换号 / 重启 | **无效** | 可能有效 |

> 2026-10-13 一天内两次因分不清二者而误判（CHANGELOG 2.0.53 / 2.0.54），本面板即该问题的闭环。

---

## 2. 数据契约

**复用既有接口，不新增后端**：

```
GET /workbuddy-pool/v1/status        ← api.getWorkbuddyPoolStatus()
```

| 字段 | 来源 | 用途 |
| --- | --- | --- |
| `accounts[].region` | 账号库 `domain` 后缀（`.ai→intl`，其余→cn）| region 分组 |
| `accounts[].disabled` | session 死亡（12153）| 出池判定 |
| `accounts[].until` / `cooldown_kind` | 账号级冷却（软限流/积分）| 冷却判定 |
| `accounts[].breaker_until` | 熔断截止 | **服务故障**的核心信号 |
| `accounts[].model_cools[]` | 模型级冷却（`model`/`until`/`reason`/`reset_at_parsed`）| **配额不足**的核心信号 |
| `accounts[].in_flight` | 在途并发 | 占用观测 |
| `credits` / `success_count` / `err_total` | 巡检 + 累计计数 | 健康度指标 |

服务端数据源：`accounts.json` + `workbuddy_gateway_state.json`。

⚠️ 组件**自行按 `accounts[].region` 分组**，不依赖后端 `regions` 聚合字段 ——
这样旧后端（无该字段）也能渲染，且分组口径与明细表**天然一致**。

---

## 3. 判据（核心）

`judgeRegion(accounts, now)` —— **分支顺序即优先级**：

| # | region 状态 | 结论 | 依据 |
| --- | --- | --- | --- |
| ① | 无账号 | ⚪ 结构性缺号 | `accounts.length === 0` —— 不是限流也不是故障，是池里没配 |
| ② | 有健康号 + 无模型限流 | 🟢 可用 | `!disabled && until<=now && breaker<=now`（与后端 `Entry::healthy` **同口径**）|
| ③ | 有健康号 + 有模型限流 | 🟡 **部分模型限流** | 账号能用，但**你要的模型**可能被限 |
| ④ | 无健康号 + 有熔断/出池 | 🔴 服务故障 | 熔断由**连续失败**喂出，指向链路问题，且需人工介入 |
| ⑤ | 无健康号 + 全部被模型级冷却 | 🟡 配额不足 | `model_cools` 命中 ⇒ 上游对该**模型**的频率上限 |
| ⑥ | 无健康号 + 仅软冷却 | 🟠 冷却中 | 429 类限流退避，会自行恢复 |
| ⑦ | 以上都不命中 | ⚪ 原因未知 | **不猜** —— 宁可说不知道，也不给错结论 |

### 🔴 两条不可动摇的约束

**约束一：「有账号可用」≠「你要的模型能用」。**
首版在 `healthy > 0` 时直接返回「可用」，忽略模型级冷却 —— 于是 intl 区明明
`deepseek-v4.1-flash` 已被限流、面板却显示 🟢 可用，而实际请求 503。
**这是比不显示更糟的误导**，故新增 `partial` 档位，并要求结论文案
**点名被限流的模型与恢复时间**（否则用户知道有问题也无法处置，脚本里有对应断言）。

**约束二：「模型级冷却」不计入池健康。**
被限的是某个**模型**，账号本身仍健康。若把它算作「账号不可用」，
就会把「配额问题」误报成「区域不可用」。故它只出现在结论文案与明细表「模型限流」列。

## 4. 界面结构

```
┌─ 账号池健康 · region 可用性 ──────────────── [刷新] ┐
│ 数据源 /workbuddy-pool/v1/status · 每 60 秒自动刷新  │
├─────────────────────────────────────────────────────┤
│ 账号总数 │ 可用 │ 账号级冷却 │ 熔断 / 模型限流        │  ← 总览计数（异常变色）
├─────────────────────────────────────────────────────┤
│ ● cn    可用     2/2 账号可用                        │  ← region 结论区
│   └ 2/2 个账号可参与选号。                           │     （异常时整行上色）
│ ● intl  配额不足  0/1 账号可用   模型限流 1 个        │
│   └ 账号本身健康，但它被上游按模型限流：              │
│     deepseek-v4.1-flash（10-13 22:59 恢复）          │
├─────────────────────────────────────────────────────┤
│ 账号 │ 区 │ 状态 │ 积分 │ 成功/失败 │ 在途 │ 模型限流 │  ← 明细表
├─────────────────────────────────────────────────────┤
│ 怎么读：配额不足 = 换号/重启都没用…                   │  ← 判读提示（写在界面上）
└─────────────────────────────────────────────────────┘
```

### 异常高亮规则

| 状态 | 视觉 |
| --- | --- |
| 熔断 / 已出池 | 整行红底 + 状态列红字 + 显示截止时间 |
| 模型限流（配额）| 整行琥珀底 + 显示模型名与恢复时间 |
| 限流冷却 | 状态列橙字 + 截止时间 |
| 健康 | 状态列绿字 |

---

## 5. 刷新频率与依据

| 项 | 取值 | 依据 |
| --- | --- | --- |
| 轮询间隔 | **60s** | 冷却/熔断的时间尺度是**分钟级**（软冷却基准 600s、模型冷却按上游重置时间）；更快轮询只会空转 |
| 手动刷新 | 提供按钮 | 排障时不想等 |
| 失败处理 | 首次加载失败显示错误卡 + 「重试」 | 已有数据时不打断渲染（静默保留上次结果）|

## 6. 集成方式

组件**自包含**（自己取数、自己轮询），集成只需两步：

```tsx
import { PoolHealthPanel } from "@/components/pool-health-panel";

// 放到任意页面/区块
<PoolHealthPanel />
```

当前挂载点：`pages/WorkBuddyMonitorPage.tsx`（统计页 → **WorkBuddy 逆向** Tab）**置顶**。
选这个位置的依据：该页一旦出现失败，第一个要回答的就是「配额还是故障」——
**把答案放在症状上面**。

## 7. 已知边界

- `reset_at_parsed=false` 的模型冷却，`reason` 会带「未取到重置时间，按软冷却 X 处理」——
  说明该时间来自本地退避而非上游，**不代表上游真会那时恢复**。
- 组件不做**端口/出口连通性**探测（那需要真实请求）；它只反映**选号视角**的可用性。
  出口不通会表现为账号熔断，仍能被本面板捕捉。
- 模型限流按「区 × 模型」聚合；要看单个账号，见明细表「模型限流」列。
